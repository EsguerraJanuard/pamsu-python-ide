## Part 1: AST evaluation (`evaluate_ast_details`)

### How the checks work

- 33 programs: 30 valid programs and 3 with a deliberate syntax error.
- Each valid program is checked for 7 rules. The expected count for every rule was written by hand from the Python language rules, not taken from the evaluator. A zero is a check too: it catches false positives.
- Rules are passed in the shape the activity editor saves: `{rule_id: {"required": True, "min_count": n}}`.
- Each valid program runs 6 times: required count 1 and 2, under strict, moderate and lax.
- **Count check** (one per program and rule): all of those runs must report `detected_count` equal to the hand count.
- **Verdict check** (one per program, rule, required count and mode): the finding's `passed` value must match the mode's meaning as the instructor screen describes it (`frontend/src/utils/astRules.js`): strict = exactly the required count; moderate = at least the required count; lax = at least once, whatever count is set. The expected verdict is computed from the hand count, so a counting error would also show up here.
- In 83 of 420 (program, rule, required count) combinations the three modes should give different verdicts, so the test exercises the differences between the modes, not only cases where they agree.
- **Syntax-error check**: for each broken program and each mode, the result must report `syntax_error`, `passed = False` and no findings; and the reported line must match.

### Notes on the AST results

- `elif` is stored by Python as an `if` nested in the `else` branch, so an `if / elif / else` chain counts as 2 if statements (A02), the same as an `if` written inside `else` (A16). In **strict** mode with a required count of 1, such a chain therefore fails. This is the intended counting, but instructors who use strict mode should set the count to the number of `if` plus `elif` branches.
- Conditional expressions (`x = 1 if a else 2`), comprehension filters (`[x for x in y if x > 0]`) and `match` case guards are different syntax nodes, so they are not counted as if statements (A04, A05, A10, A24, A29).
- The `for` inside a list, set or dict comprehension or a generator expression is not a for loop (A09 to A13, A29). `async for` and `async def` do count as a for loop and a function definition (A20).
- Keywords inside comments, strings and docstrings are not counted (A21, A22), because the evaluator reads the syntax tree, not the text.
- Lax mode ignores the required count once a structure appears at least once. With a required count of 2, a program with one for loop passes in lax and fails in moderate and strict, as the instructor screen says.

## Part 2: Jaccard similarity (`calculate_jaccard_score`, shingle size 3)

### How the score works

Both programs are parsed into syntax trees and reduced to a sequence of node types and operators (`app/services/ast_fingerprinter.py`). Variable names, function names and literal values are dropped; comments and spacing never reach the tree. The sequence is cut into overlapping runs of 3 node types (shingles), and the score is |shared shingles| / |all shingles| x 100. For example, `total = a + b` becomes `Module Assign BinOp Add`. The platform shows this score to the instructor as a review indicator; it has no automatic threshold and never flags plagiarism by itself.

Each base program was compared with seven variants. Same-task variants were run with fixed inputs to confirm they print the same output as their base (50 of 50 checks matched (100%)).

### Interpretation

- **Lexical changes** (exact copy, renamed variables, comments, spacing, literal values): 15 of 15 checks matched (100%). Renaming and reformatting a program does not lower the score.
- **Reordered statements** scored 41.18% to 60.00% (mean 50.40%). The score compares runs of 3 consecutive node types, so statement order matters. In J1, two lines swap places, but the fingerprint is only 18 node types long, so 8 of the 20 distinct shingles across the two programs are not shared. With order ignored (shingle size 1) the same reordered copies average 100.00%.
- **for rewritten as while** scored 14.29% to 46.43% (mean 29.12%). The loop node changes from `For` to `While`, and the counter adds an assignment and an update.
- **Independent solutions** scored 0.00% to 14.29% (mean 7.48%; highest J1). Each one takes a different approach (a built-in function, recursion or a comprehension), which gives a different syntax tree.
- **Different tasks** scored 0.00% to 12.50% (mean 5.53%; highest J1). At shingle size 3, unrelated short programs share little structure.
- Every reordered copy (lowest 41.18%) still scored above every independent solution (highest 14.29%) and every different-task program (highest 12.50%), so a reordered copy still stands out when the instructor compares submissions.
- The ranges for while rewrites and independent solutions overlap: the lowest rewrite (J2, 14.29%) scored no higher than the highest independent solution (J1, 14.29%).

### Documented limitations

1. **Independent work with the same approach looks like a copy.** The independent solutions above scored at most 14.29% only because each takes a different approach. A second student who writes the standard loop for J1 on their own scores **100.00%** (first probe below). Short tasks have few natural solutions, so honest students often produce the same structure. This is the main reason the platform shows the score to the instructor as a review indicator and never as an automatic verdict.
2. **Reordering statements lowers the score sharply on short programs** (41.18% to 60.00% here), because each moved statement changes a large share of a short program's shingles.
3. **Rewriting a for loop as a while loop can push a copy down into the range of independent solutions** (lowest rewrite 14.29%, highest independent solution 14.29%).
4. **Names are fully ignored, including function names.** This is what makes renaming score 100%, but it also means `sum(values)` and `len(values)` look the same (probe below).
5. **Docstrings count as statements.** Unlike `#` comments, a docstring is a string expression in the syntax tree, so adding one lowers the score slightly (probe below).
6. **Programs with syntax errors are compared differently.** If either program does not parse, `jaccard.py` falls back to comparing normalized tokens. That path is not measured here: all Part 2 programs parse (35 of 35 checks matched (100%)).
