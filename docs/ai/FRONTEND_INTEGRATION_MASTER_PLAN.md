## 2. API Configuration (Centralized apiFetch)
The frontend currently utilizes native `fetch` scattered across components.
**Correction**: Do not use the term "fetch interceptor."
Instead, the Integration Member must implement a centralized `apiFetch` wrapper (`frontend/src/services/apiFetch.js`) that:
- Reads `VITE_API_BASE_URL` from the environment.
- Adds `Authorization: Bearer <token>` when authentication is required.
- Supports both `application/json` and `application/x-www-form-urlencoded`.
- Parses JSON, text, and empty responses safely.
- Explicitly handles `401 Unauthorized`, `403 Forbidden`, `404 Not Found`, `409 Conflict`, `422 Unprocessable Entity`, `429 Too Many Requests`, `500 Internal Server Error`, `503 Service Unavailable`, and network failures without crashing.
- **SECURITY BOUNDARY**: Under no circumstances should `apiFetch` log tokens, passwords, OTPs, source code, or sensitive payloads to the console or any monitoring service.

## 3. Authentication Storage & Profile Configuration
An inspection of `frontend/src/features/auth/AuthContext.jsx`, `frontend/src/features/auth/Login.jsx`, `frontend/src/features/auth/ProtectedRoute.jsx`, `frontend/src/features/auth/RoleRoute.jsx`, and `frontend/src/App.jsx` reveals that authentication currently assumes immediate `localStorage` storage of token and user data.

**Backend JWT Creation Code Inspection:**
The backend JWT (`create_access_token`) explicitly includes these claims: `sub` (user_id), `role`, `name`, `email`.
*Limitation*: `school_id` and `email_verified` are NOT within the JWT, though they are present in the `AuthenticatedUserResponse` upon login.
Frontend decoding may only be used for interface state and routing convenience. Backend authorization remains authoritative.

**Approved Token-Storage Decision:**
- **Selected Storage**: Access token in `sessionStorage`.
- **User State**: Hydrated user state in `AuthContext`.
- **Token-clearing behavior**: Clear token and user state on logout, token expiry, and 401.
- **Security Implications**: Never persist passwords or OTPs.
- **Authoritative Source**: Backend authorization remains authoritative.

## 4. Settings Configuration (Contract Blocked)
Based on the **Backend 1.0.0 Final OpenAPI Contract**:
- There is **no endpoint** for retrieving the current user's editable profile.
- There is **no endpoint** for updating a user profile.
- There is **no endpoint** for changing the password.
**Conclusion**: Both `frontend/src/features/settings/Settings.jsx` and `frontend/src/features/settings/InstructorSettings.jsx` are currently **display-only** or **contract-blocked**. They cannot be integrated for updates until the backend contract is revised in a future version.

## 5. Registration Readiness Separation
Registration has two distinct readiness factors:
1. **Frontend API integration**: Registration-start API wiring may proceed after UI go signal.
2. **OTP Verification**: OTP verification end-to-end validation is externally blocked until an approved delivery or development testing mechanism exists.

## 11. Strict System Boundaries Reminder
- The frontend handles untrusted student-authored source text, while execution remains isolated outside React and FastAPI.
- Hidden tests are never exposed to the frontend JSON payload.
- No automatic grading; automated checks are indicators only.
- No automatic plagiarism or misconduct verdicts.
- No clipboard-content or pasted-text collection (aggregate counts/timestamps only).
- Production OTP email and isolated sandbox execution remain external dependencies.
